## 一、需求复述（对齐三方共识）

**目标：** 在三大支柱（执行层/安全层/认知层）之上建立一个**协调层**，解决三个核心问题：
1. 全局协同缺失（项目间、版本间无统筹）
2. 反馈机制缺失（项目落地后无状态回传、阶段衔接断裂）
3. 主导者能力担忧（无仪表盘，只能靠全知驾驭——GLM 判断为前两问题的后果）

**GLM 方案核心：** 元管理层 = 项目地图 + 版本账本 + 心跳监控 + 决策日志；先考古还原真相，再定基准运行；从 Markdown 起步不写代码。

**瑶光验证结论：** 方向认同；落地基础已过半（inventory/feedback-log/health-cron 已存在）；需补三件事——新建版本账本、部分自动化、挂靠 governance 强制纪律。

## 三、详细设计要点

### 3.1 项目地图（PROJECT_MAP.md）
- **数据来源：** 合并 project-inventory.md + project-overview.md，去重、标日期
- **条目结构：** `项目名 | 状态机阶段 | 依赖(上游/下游) | 负责人(先生/瑶光/GLM) | 最近变更 | 下一步`
- **已知依赖链（实测）：**
  ```
  备份方案 v2.2 ──等待──> 第零章 0.1+0.2（Key 迁移 .env）
  多Agent协作 v3.1 ──reflector 退役待执行（07-28 逾期）
  记忆系统 Phase 2 ──等待验证结果决策
  3-A 情境感知 ──完全独立，可随时启动
  ```

### 3.2 版本账本（VERSION_LEDGER.md）
- **核心概念：** 配置漂移记录 = "文档声称 vs 实际存在"的偏差表
- **首批数据（07-31 实测考古）：**
  | 项目 | 文档声明 | 实际状态 | 漂移 | 处理 |
  |------|---------|---------|------|------|
  | 多Agent v3.1 | reflector 07-28 退役 | 仍每日 03:00 运行 | 🔴 逾期 5 天 | 退役执行 |
  | 记忆系统验证 | 08-01 20:00 检查 cron 已就位 | cron 不存在 | 🔴 从未创建 | 补建或改手动检查点 |
  | 微信投递 | 通道已移除 | 12 个 disabled cron 残留 | 🟡 残留 | 批量清理 |
  | 记忆系统 | v2.6-final 为当前版 | archive/ 10 份旧版并存 | 🟡 堆积 | 归档整理 |
  | openclaw.json | 当前配置 | 9 份 .bak 残留 | 🟡 堆积 | 保留最近 2 份，其余归档 |
- **更新规则：** 任何落地动作（含补丁）完成后 24h 内回写账本；L2 一致性检查每周对账一次

### 3.3 心跳监控
- **L0 存活（每日）：** 复用"每日服务器健康检查"cron（已存在），输出追加元管理层日报摘要
- **L1 健康（每周）：** 复用"每周日配置备份与周报"cron（已存在），周报新增：各项目状态机阶段 + 漂移项进展
- **L2 一致性（每次变更后 + 每周对账）：** **新增 cron**，脚本扫描：
  1. VERSION_LEDGER 中"处理中"漂移项是否过期
  2. 项目状态机是否有"应退役未退役"（对比 cron list / agents 注册）
  3. 设计文档声明的 cron/文件/配置是否实际存在
  4. 产出异常清单 → announce 给先生
- **原则：** 元管理层自身必须有自动化底座，不依赖"瑶光自觉"（已证明靠自觉必败：reflector、验证 cron 两例）

### 3.4 决策日志（DECISION_LOG.md）
- **升级 feedback-log.md**，模板扩展：
  ```
  ### 日期 — 决策标题 [tag]
  **背景：** ...
  **决策：** ...
  **理由：** ...
  **影响范围：** <涉及哪些项目/支柱>
  **后续观察：** <何时验证、验证标准>
  **验证结果：** <回填>
  ```
- **强制纪律：** 写入 rules.md——"重大变更（🔴/🟡级）决策必须当日写日志，Auditor/检查 cron 核对"

### 3.5 强制纪律层（瑶光补充，GLM 方案未含）
- 变更流程：`查 PROJECT_MAP（依赖影响）→ 查 VERSION_LEDGER（漂移现状）→ 执行 → 更新 VERSION_LEDGER + DECISION_LOG → 触发 L2 检查`
- 违规处理：未回写 → findings/ 记录 → 周报点名 → 先生裁决
- 挂靠点：governance/rules.md（已有）+ findings/（已有）+ Auditor 设计（已有）

## 四、落地路线（三阶段）

### 阶段 A：考古收尾 + 基线建立（半日内）
1. 补全"运行中补丁"清单（先生指出"补丁未记录"的空白区）
2. 一次性清理：reflector 退役、12 个 disabled cron、版本文件归档
3. 建立 PROJECT_MAP.md + VERSION_LEDGER.md（从现有资产合并迁移）

### 阶段 B：机制运行（1 周验证期）
4. 升级 HEARTBEAT/周报模板，接入 L0/L1
5. 新增 L2 一致性检查 cron
6. 升级 DECISION_LOG 模板 + rules.md 写入变更纪律

### 阶段 C：审计闭环（验证期后）
7. Auditor 部署或过渡方案（每日 cron 代行审计）
8. 元管理层自检：账本漂移率作为自身健康指标，进入周报

## 五、异常处理与风险

| 风险 | 影响 | 对策 |
|------|------|------|
| 元管理层自身文件漂移（文档 vs 实际） | 机制失效，重蹈覆辙 | L2 检查包含"元管理层自身文件"；账本漂移率进周报，连续 2 周超标 → 触发人工复盘 |
| 自动化检查误报/漏报 | 先生信任下降 | 检查项先人工复核 1 周（阶段 B），再放行自动 announce |
| 清理动作破坏运行配置 | 服务中断 | 遵循先备份原则：清理前 snapshots/ 快照（已有 pre-change-snapshot.sh）；reflector 退役保留配置备份 7 天 |
| 与已有 governance/ 框架职责重叠 | 双轨混乱 | 明确边界：governance = 规则与纪律；元管理层 = 状态与协调；版本账本为两者共享数据源 |
| GLM 评审提出更优结构 | 返工 | 本表为对照表非定稿，结构变更成本低（纯 Markdown 迁移） |
