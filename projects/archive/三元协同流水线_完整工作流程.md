## 二、角色职责

### 先生（决策者）
- 提出需求 → 确认方案 → 做出最终决策 → 拍板落地
- 不需要做技术实现判断，做老板决策
- 做以下类型的决策：方案方向切换、安全策略调整、长期记忆修改、架构设计变更

### 主 Agent（DeepSeek V4 Flash）
- 需求分析、方案设计、任务执行、产生审查指令包
- 不自审（不自查自己的方案）
- 不中转审查结果（GLM 的审查结果完整转发先生，不删减不缩写）
- 调度 GLM 审查、执行治理清理、处理 handoff/ 消息

### 持久 GLM Agent（GLM-5.1）
- 持久存在（不是用完即走的临时子 Agent）
- 技术评审者：审查方案、发现缺陷、评估风险
- 通过 handoff/ 文件异步接收审查请求、输出审查结果
- 有自己的 workspace 和 AGENTS.md

### Reflector（GLM-5.1）
- 每日 03:00 自动运行
- 事后反思：扫描手递目录、长期记忆、治理状态
- 记忆治理：发现过期/矛盾/低质量记录，生成治理建议
- 架构健康度：手递死信、治理执行率、审查规则执行度

### 子 Agent（sessions_spawn）
- 探索子 Agent：只读权限，做环境盘点、信息收集
- 落地验证子 Agent：执行后机械式核对（三对照原则）
- 用完即删（`cleanup: "delete"`），发现物由主 Agent 人工提取

## 三、通信协议

### 3.1 两种通道

| 通道 | 方式 | 用途 | 上下文影响 |
|------|------|------|:----------:|
| sessions_send | 一对一直连 | 短摘要确认/前驱上下文 | 少量 token，每日重置 |
| handoff/ 文件 | 异步文件读写 | 详细审查/方案/反思 | 不进对话上下文 |

### 3.2 sessions_send 调用规范

**向 GLM 发消息时，message 必须包含：**

```markdown
## Context
<3–5 句话概括讨论背景，包含前因后果>

## Question
<具体要问的问题或要评审的内容>

## Priority
🔴 | 🟡 | 🟢
```

禁止不带上下文直接抛问题。

**接收 GLM 回复的规范：**
- GLM 的详细审查意见走 handoff/ 文件，不会通过 sessions_send 全文发送
- sessions_send 仅含简短状态摘要：如"已评审完毕，见 handoff/xxx.md，剩余🔴问题0个"
- 收到摘要后去读对应 handoff/ 文件获取完整内容
- 仅当需要追问时才继续 sessions_send 来回

### 3.3 handoff/ 文件名后缀状态机

| 文件模式 | 状态 | 含义 |
|----------|:----:|------|
| `xxx-from-A-to-B.md` | open | 待处理 |
| `xxx-from-A-to-B.in-progress.md` | in-progress | 处理中（可选） |
| `xxx-from-A-to-B.resolved.md` | resolved | 已完成 |
| `xxx-from-A-to-B.rejected.md` | rejected | 拒绝处理（可选） |

### 3.4 Ping-Pong 截断处理

当与 GLM 的 ping-pong 对话达上限终止时：
1. 末轮标注 `[PING-PONG_LIMIT_REACHED]`
2. 未讨论完问题写入手递 `pingpong-residue-<日期>-from-deepseek-to-glm.md`
3. 状态通过文件后缀标记

## 四、任务优先级分级

### 4.1 三级分类

| 级别 | 含义 | 审查流程 | 迭代上限 |
|:----:|------|---------|:--------:|
| 🔴 | **高风险**：影响核心决策、安全、长期架构 | 完整审查 → 直达先生 | 10轮 |
| 🟡 | **常规**：方案讨论、日常评审 | 标准审查 → 抄送先生 | 5轮 |
| 🟢 | **低风险**：确认性提问、简单信息查询 | 默认免审，除非有明确风险 | 3轮 |

### 4.2 分级执行规则

- **分级是发起方的责任。** 评审方（GLM）可以质疑定级，但不替代定级
- 🔴 审查结果 **直达先生**（sessions_send 或 handoff）
- 🟡 审查结果 **发 DeepSeek + 抄送先生**
- 🟢 审查结果 **只发 DeepSeek**（默认免审）

## 五、7 阶段标准流程

```
[阶段 1：环境探索]（可选，🔴 任务前置）
  探索子 Agent → 环境盘点 → 附入审查指令包

[阶段 2：方案设计 + 审查指令包]
  主 Agent 产出方案 + 审查指令包

[阶段 3：异步审查]
  主 Agent 写 handoff/xxx-from-deepseek-to-glm.md
  → GLM 读到 handoff（open 状态）
  → GLM 逐条审查 → 输出 .resolved.md

[阶段 4：决策]
  主 Agent 读 GLM 审查结果 → 完整转发先生
  先生决策：通过 / 有条件通过 / 不通过

[阶段 5：执行落地]（通过后）
  主 Agent 按方案执行改动

[阶段 6：落地验证]（🔴 任务强制）
  落地验证子 Agent → 三对照核对

[阶段 7：事后反思]（异步，每日 03:00）
  Reflector 读 handoff/ + long-term/ → 反思 + 治理
```

## 六、审查指令包规范

### 6.1 固定审查基线（6条——不可删减）

| 编号 | 检查项 | 问法 | 审查方法 |
|:----:|--------|------|---------|
| 1 | **需求覆盖** | 我要的事方案全管到了吗？ | 逐条对照原始需求 |
| 2 | **内部一致性** | 方案各部分有矛盾吗？ | 检查逻辑冲突 |
| 3 | **可落地性** | 用的工具资源我手上真有吗？ | 逐项检查环境可用性 |
| 4 | **异常处理** | 出错怎么办？ | 检查失败场景覆盖 |
| 5 | **过度设计** | 有没有实际用不上的东西？ | 逐模块检查必要性 |
| 6 | **假设透明** | 哪些前提假设？ | 列出所有隐含假设 |

### 6.2 审查指令包结构

```
========================================
审查指令包
========================================

[先生需求原文]
（复述先生提出的任务需求）

[第一部分：固定基线——6条]
1. 需求覆盖 ...
2. 内部一致性 ...
...（逐条列出，不可删减）

[第二部分：本次补充验证点]
建议验证方向：
1. ...
2. ...
已知风险：
- ...

⚠️ 提示 GLM：以上列表可能不完整，GLM 应独立补充至少 2 条未提及的风险点。

[第三部分：设计假设]
1. ... → 若不成立，影响...
2. ...

[待审查方案]
（方案全文）
========================================
```

### 6.3 严重程度与决策权映射

| 严重程度 | 含义 | 默认决策 |
|:-------:|------|---------|
| 🔴 **致命** | 方案核心逻辑错误，无法执行 | 自动不通过，必须修改 |
| 🟠 **严重** | 方案有明显缺陷 | 自动有条件通过 |
| 🟡 **一般** | 有优化空间，不影响核心逻辑 | 建议，不阻塞通过 |
| ⚪ **建议** | 非必须，值得考虑 | 记录备选 |

## 七、审查结果直达先生

### 7.1 审查结果转发规则

GLM 审查结果完成后，主 Agent 必须：

1. **完整转发** GLM 原始审查结果给先生，不得删减、缩写、选择性转述
2. 可在前面附**摘要**（标注"以下为摘要"），但不能替代原文
3. 可在后面附**"我的回应"**（标注不同意的条目及理由）

### 7.2 行为序列约束

收到 GLM 审查结果后，**第一动作必须是**：将原始内容完整粘贴到代码块中。粘贴完成之前不得生成任何分析、摘要或回应。

### 7.3 先生决策选项

| 选项 | 适用场景 |
|------|---------|
| 通过 | 方案满意 |
| 有条件通过 | 调整细节后通过 |
| 不通过 → 继续审查（+2轮） | 方向对但细节不够 |
| 不通过 → 叫停重来 | 方向不对 |

## 八、反思触发链路

### 8.1 主动触发

```
先生："反思一下最近的讨论"
     ↓
主 Agent 写 handoff/xxx-trigger-reflect.md
     ↓
先生执行：openclaw cron run --job reflector --mode force
  或等待每日 03:00 自动运行
```

### 8.2 自动触发（每日 03:00）

Reflector 每天 03:00 自动执行：
1. 检查手递中是否有定向指令
2. 有 → 按指令定向反思
3. 无 → 全量反思（扫描 handoff/ + long-term/ + memory/）
4. 输出反思报告 + 治理建议 + 架构健康度
5. 标记手递指令为 resolved

## 九、长期记忆治理闭环

```
[每日 03:00] Reflector 扫描 long-term/
 → 识别矛盾决策、过期记录
 → 输出治理建议到 reflections/long-term-maintenance/

[运行时] 主 Agent 检查治理目录
 → 有新建议 → 向先生汇报
 → 先生确认 → 主 Agent 执行清理
 → 更新 processed.json 避免重复汇报
```

## 十、审查反馈闭环

### 10.1 反馈采集

每次审查走完后，主 Agent 主动问一次先生反馈：

> "先生，这次 GLM 审查有哪条查得好、哪条跑偏了？"

### 10.2 反馈记录

记录到 `review-feedback.json`：

```json
{
  "reviews": [{
    "task": "任务名称",
    "date": "日期",
    "rating": 4,
    "valuable": ["第3条异常处理查得准"],
    "false_positive": ["第2条认为过度设计，但实际必要"],
    "missed": ["没检查外部依赖版本兼容性"]
  }]
}
```

### 10.3 降频规则

连续 3 次先生回"没问题" → 第 4 次起降级为月度汇总
月度汇总连续 2 次不回 → 暂停，等主动提

### 10.4 教训库触发

积累 ≥3 条 false_positive / missed 记录 → 自动评估是否建立审查教训库

## 十一、异常处理

| 异常情况 | 处理方式 |
|---------|---------|
| GLM 对话未激活（长时间无切换） | 主 Agent 提示先生切到 GLM 对话 |
| GLM 输出格式不符合规范 | 按结构化模板手动整理，缺失标注"GLM 未提供" |
| 探索子 Agent spawn 失败 | 重试 1 次 → 仍失败手动检查 |
| 落地验证子 Agent spawn 失败 | 重试 1 次 → 降级为主 Agent 手动核对 |
| 反馈积累 ≥3 条误报/遗漏 | 自动评估建立教训库 |

## 十三、与旧 C+ 模式关键差异

| 维度 | C+ 模式（已废弃） | 三元协同流水线 |
|------|:---------------:|:-------------:|
| 审查方式 | spawn 子 Agent + curl 硅基流动 | handoff/ 文件 → 持久 GLM Agent |
| 审查速度 | 同步（秒级） | 异步（需切换对话） |
| 依赖中转 | 硅基流动 API | 无中转 |
| 上下文连贯性 | 无（每次从零开始） | 有（GLM 可回顾历史 handoff） |
| 审查记录 | 子 Agent 上下文丢弃 | handoff/ 文件永久保留 |
| GLM 模型 | 硅基流动的 GLM-5.2 | 直连持久 GLM-5.1 |
| 探索子 Agent | 保留 | 保留 |
| 落地验证子 Agent | 保留 | 保留 |
| Reflector | 无 | 新增（每日 03:00 反思） |
| 长期记忆治理 | 无 | handoff/ + long-term/ 闭环治理 |
