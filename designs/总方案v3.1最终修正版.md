## 一、设计哲学

### 1.1 七条核心原则

| 编号 | 原则 | 出处 | 在架构中的体现 |
|------|------|------|-------------|
| P1 | 按上下文可隔离性拆分，不按职能拆分 | 资料1+2 | 探索/验证/Auditor黑盒可隔离；GLM半白盒可隔离；瑶光第三层不可隔离自己做 |
| P2 | 三层隔离：工具集+Prompt+权限 | 资料1 | 每个Agent有agent profile配置+system prompt+运行时隔离 |
| P3 | 验证是最安全的第一刀 | 资料3 | 验证Agent是黑盒落地验证；GLM是半白盒方案审查 |
| P4 | 从最简单模式起步，按真实瓶颈演进 | 资料4+5 | 🟢→🟡→🔴三条路径，按需触发Agent |
| P5 | 模式是积木不是菜单 | 资料5 | Orchestrator（瑶光调度）+ Generator-Verifier（GLM审查回路）+ 轻量Shared State（findings/缓冲区） |
| P6 | 防偷懒四铁律 | 资料3 | 每个Agent有具体标准+全面检查+独立补充+强起始句 |
| P7 | 行为规范写成制度 | 资料1 | 方案文档强制结构+行为序列约束+AGENTS.md规则 |

### 1.2 三个基本原则（继承旧方案）

1. **从简单开始** — 🟢任务瑶光全包，不触发任何子Agent
2. **硬约束兜底，软约束补缝** — 工具集隔离是硬约束，prompt约束是软约束，行为序列是半硬约束
3. **不信任模型的自觉性** — 能用规则写清楚的绝不留给模型临场判断

### 1.3 核心改造（v2.0 → v3.0）

| 改造点 | v2.0 | v3.0 | 理由 |
|--------|------|------|------|
| 拆分维度 | 按职能（生成/审查/反思） | 按上下文可隔离性 | P1 |
| GLM角色 | 白盒技术评审者 | 半白盒方案质量审查员 | P1+P3 |
| Reflector | 白盒事后反思 | 黑盒系统审计员（Auditor） | P1+P3 |
| 流程 | 固定7阶段线性流水线 | 按优先级3条路径动态路由 | P4+P5 |
| 反思职责 | 外包给Reflector | 瑶光自己做（有完整上下文） | P1 |
| 子Agent发现 | 随session关闭丢失 | findings/缓冲区+三条提取路径 | P5 Shared State |
| 验证Agent | 临时spawn | 持久存在 | 先生直查看硬约束 |
| GLM触发 | 🔴+🟡 | 仅🔴 | 成本控制 |

## 四、任务动态路由

### 4.1 三条路径

```
先生需求到达
 │
 ▼
瑶光判定优先级（标注理由）
 │
 ├─ 🟢 轻量路径
 │ 理解需求 → 简化方案 → 执行 → 自检 → 交付先生
 │ 不触发任何子Agent
 │
 ├─ 🟡 标准路径
 │ 理解需求 → 简化方案文档 → 执行 → 生成验证包 → 验证Agent验证
 │ → PASS：交付先生 / FAIL：修复重验
 │ 不触发探索Agent和GLM
 │
 └─ 🔴 完整路径
 │ 子判定：需要环境探索吗？
 │ ├─ 需要 → 探索Agent → 完整方案文档 → 生成检查包 → GLM审查
 │ └─ 不需要（纯设计）→ 直接进完整方案文档 → 生成检查包 → GLM审查
 │ → 先生决策 → 执行 → 生成验证包 → 验证Agent验证
 │ → PASS：交付先生 / FAIL：修复重验
 │ → findings提取 → 费用估算
```

### 4.2 分级标准

| 级别 | 包含范围 | 路径 | 先生介入 |
|:----:|---------|------|:--------:|
| 🔴 | 方案设计/架构决策/安全配置/外部接入/涉及金钱/先生指定 | 完整路径 | 必须看结果并拍板 |
| 🟡 | 代码实现/文档输出/信息整理（方案已确定） | 标准路径 | 可秒阅确认 |
| 🟢 | 简单查询/日常提醒/先生说"直接做" | 轻量路径 | 无需介入 |

### 4.3 各路径阶段映射

| 阶段 | 🟢 | 🟡 | 🔴 |
|:----:|:--:|:--:|:--:|
| 1. 路由判定 | ✅ | ✅ | ✅ |
| 2. 环境探索 | — | — | ⚠️按需 |
| 3. 方案设计 | 简化 | 简化版 | 完整版 |
| 4. 提交GLM | — | — | ✅ |
| 5. 转发GLM结果 | — | — | ✅ |
| 6. 执行落地 | ✅ | ✅ | ✅ |
| 7. 提交验证 | — | ⚠️可选 | ✅强制 |
| 8. 接收验证结果 | — | ⚠️可选 | ✅ |
| 9. findings提取 | — | ✅ | ✅ |
| 10. 治理执行 | ✅ | ✅ | ✅ |
| 11. 费用估算 | — | — | ✅ |

### 4.4 路由判定规则

```markdown
1. 每次判定优先级时，必须标注判定理由
 格式：[建议分级：🔴/🟡/🟢] 理由：XXX
2. 先生可随时覆盖判定
3. 首次出现的任务类型默认🟡，后续根据先生反馈调整
4. 以下情况自动判定为🔴：
 - 涉及方案设计或架构决策
 - 涉及配置修改或权限变更
 - 涉及外部系统接入
 - 涉及金钱操作
 - 先生明确指定
5. 以下情况自动判定为🟢：
 - 先生说"直接做"
 - 简单查询（时间、天气、文件内容）
6. 不确定时宁可升级不降级
```

## 五、通信协议总览

### 5.1 通信通道

| 通道 | 方式 | 用途 | 上下文影响 |
|------|------|------|:----------:|
| 主session对话 | 先生↔瑶光 | 需求接收、结果交付、决策请求 | 主上下文 |
| sessions_spawn | 瑶光→探索Agent | 探索指令下发 | 隔离上下文 |
| announce链 | 探索Agent→瑶光 | 探索结果返回 | 返回到主上下文 |
| sessions_send | 瑶光↔GLM/验证/Auditor | 短状态通知 | 少量token，每日重置 |
| handoff/文件 | 所有持久Agent间 | 详细检查包/验证包/审查结果 | 不进对话上下文 |
| findings/文件 | 所有Agent→瑶光/Auditor | 结构化发现 | 不进对话上下文 |
| audit-reports/文件 | Auditor→瑶光/先生 | 审计报告+治理建议 | 不进对话上下文 |

### 5.2 防污染协议

- 详细审查/验证内容走handoff/文件，不进sessions_send
- sessions_send只发简短状态摘要
- 接收方看到摘要后再去read对应handoff文件获取完整内容

### 5.3 handoff/文件名状态机

| 文件模式 | 状态 | 含义 |
|----------|:----:|------|
| `xxx-from-A-to-B.md` | open | 待处理 |
| `xxx-from-A-to-B.in-progress.md` | in-progress | 处理中（可选） |
| `xxx-from-A-to-B.resolved.md` | resolved | 已完成 |
| `xxx-from-A-to-B.rejected.md` | rejected | 拒绝处理（可选） |

### 5.4 sessions_send消息规范

```markdown
## Context
<3-5句话概括讨论背景，包含前因后果>

## Question
<具体要问的问题或要评审的内容>

## Priority
🔴 | 🟡 | 🟢
```

禁止不带上下文直接抛问题。

### 5.5 Ping-Pong截断处理

当瑶光与GLM/验证Agent的ping-pong对话达上限终止时：
1. 末轮标注`[PING-PONG_LIMIT_REACHED]`
2. 未讨论完问题写入handoff/目录的residue文件

## 六、findings/完整生命周期

### 6.1 findings/是轻量版Shared State

所有Agent直接读写同一个共享存储发现缓冲区，而非各自的workspace中。谁发现了什么就写进去，别人看到再接着推进。

### 6.2 findings文件统一格式（v3.1）

```json
{
  "meta": {
    "source": "explorer|verifier|glm|auditor",
    "task_id": "关联的任务ID",
    "timestamp": "ISO时间",
    "duration_seconds": "耗时",
    "status": "completed|partial|failed|timeout"
  },
  "summary": "一句话摘要",
  "overall_result": "PASS|FAIL|PARTIAL|N/A",
  "findings": [
    {
      "id": "F-001",
      "category": "environment|verification|review|audit|safety",
      "title": "发现标题",
      "detail": "发现详情（≤500字）",
      "evidence": "原始输出/证据（raw_output关键摘录）",
      "raw_file_path": "关联的原始文件路径（探索Agent使用）",
      "priority": "high|medium|low",
      "actionable": true|false,
      "status": "new|extracted|archived"
    }
  ],
  "agent_specific": {},
  "unexplored": [],
  "anomalies": []
}
```

**Agent特有字段（agent_specific）**：

| Agent | agent_specific内容 |
|:-----:|:------------------:|
| 探索Agent | `blockers[]`, `raw_file_paths[]` |
| 验证Agent | `three_way_comparison{}`, `execution_log[]` |
| GLM | `reviewed_plan_version`, `check_results[]`, `remaining_critical`, `remaining_major` |
| Auditor | `audit_type`, `groups_completed[]`, `health_score`, `recommend_actions[]`, `details{}` |

### 6.3 生命周期状态机

```
new（刚写入）
 │
 ├─ 瑶光提取到long-term/ → status改为"extracted"
 │ → 7天后 → archived
 │
 ├─ 24小时无人提取 → Auditor标记⚠️遗漏风险
 │ → Auditor在审计报告中列出
 │
 └─ actionable=false → 直接archived
```

### 6.4 三条提取路径

| 路径 | 触发 | 执行者 | 机制 |
|------|------|--------|------|
| **A：主动提取** | 子Agent完成后 | 瑶光 | 读findings→判断价值→写long-term/ |
| **B：被动兜底** | 每日03:00 | Auditor | 扫描findings/→发现未提取的actionable发现→报告先生 |
| **C：任务关联** | 下一个相关任务启动时 | 瑶光 | 检索findings/中同主题记录→纳入当前任务上下文 |

### 6.5 探索Agent输出→统一格式映射表

探索Agent的输出是announce链的结构化JSON（它无write权限），瑶光收到后按此映射组装为统一findings格式：

| 探索Agent字段 | 统一字段 | 处理方式 |
|:------------:|:--------:|---------|
| `findings[].source` | `findings[].raw_file_path` | 原样保留 |
| `findings[].content` | `findings[].detail` + `findings[].evidence` | detail存完整文本，evidence存关键摘录 |
| `findings[].type` | `findings[].category` | key_value→environment, config→review, dependency→environment, 其他→review |
| `findings[].priority` | `findings[].priority` | high/medium/low（向下兼容旧P0→high等映射）|
| `findings[].actionable` | `findings[].actionable` | 原样保留，写入时置为new |
| `blockers[]` | `agent_specific.blockers[]` | 原样保留 |
| `raw_file_paths[]` | `agent_specific.raw_file_paths[]` | 原样保留 |

### 6.6 各Agent的findings产出

| Agent | source字段 | 写入方式 | 优先级判定 |
|-------|-----------|---------|-----------|
| 探索Agent | `explorer` | 瑶光代写（从announce摘要组装） | 基于发现重要性 |
| GLM Agent | `glm` | GLM自己写 | 基于失败严重程度 |
| 验证Agent | `verifier` | 验证Agent自己写 | 基于失败严重程度 |
| Auditor | `auditor` | Auditor自己写 | 基于异常严重程度 |

### 6.7 findings文件命名

```
findings/<date>_<source>_<taskName>.json

示例：
findings/2026-07-24_explorer_explorer-voice-light-001.json
findings/2026-07-24_glm_glm-voice-light-001.json
findings/2026-07-24_verifier_verifier-voice-light-001.json
findings/2026-07-24_auditor_audit-2026-07-24.json
```

## 七、🔴完整路径时序

```
先生："帮我设计一个方案"
 │
 ▼
瑶光：阶段1-路由判定
 ├─ 判定：🔴（方案设计类）
 ├─ 子判定：需要环境探索吗？
 │ ├─ 需要 → 进阶段2
 │ └─ 不需要（纯设计）→ 直接进阶段3

 ▼
瑶光：阶段2-环境探索（按需）
 ├─ 构造探索指令包（最小信息，不给背景）
 ├─ sessions_spawn({
 │ task: "<探索指令包>",
 │ taskName: "explorer-xxx",
 │ agentId: "explorer",
 │ context: "isolated",
 │ cleanup: "delete",
 │ sandbox: "inherit"
```
