# 治理闭环规则

> 最后更新：2026-07-22
> 设计：DeepSeek + GLM 评审 + 先生确认

---

## 一、治理项生命周期

```
创建（Reflector/DeepSeek）
   ↓ pending
投递（推送通知给接收方）
   ↓ delivered
确认（接收方阅读）
   ↓ acknowledged
执行中（执行治理操作）
   ↓ executed / failed
完成或失败
```

### 状态说明

| 状态 | 含义 | 触发条件 |
|------|------|---------|
| `pending` | 已创建，未投递 | 治理项产出时 |
| `delivered` | 已投递到接收方 | 推送通知成功时 |
| `acknowledged` | 接收方已阅读 | 接收方阅读时（manual/auto） |
| `executing` | 正在执行 | 开始执行操作时 |
| `executed` | 执行成功 | 操作完成无错误 |
| `failed` | 执行失败 | 操作出错或超时 |

### 重试策略

- 投递失败：最多重试 3 次，间隔 1min → 5min → 15min（指数退避）
- 执行失败：最多重试 2 次，间隔 5min → 30min
- 超过重试上限：自动升级到下一个优先级级别（🔴 级告警）
- 连续 7 天状态均为 `failed`：自动生成错误报告

## 二、白名单规则

详见 `governance/whitelist.json`，核心原则：

- **按操作类型划分**，而非按优先级标签
- 白名单内 🟢 操作 DeepSeek 自行执行
- 白名单外 🟢 操作暂缓，先生确认
- 禁止类操作即使标 🟢 也不得自执行
- 单日自执行上限 5 项

## 三、通知分发规则

```
┌─────────────┐     ┌──────────────┐     ┌──────────────┐
│  Reflector  │ ──→ │   DeepSeek   │ ──→ │    先生      │
│  产出治理    │     │  分级处理    │     │  最终裁决    │
└─────────────┘     └──────────────┘     └──────────────┘
```

| 级别 | 投递目标 | 投递方式 | 格式 |
|:----:|---------|---------|------|
| 🔴 | DeepSeek → 先生（即时） | feishu 消息 | 单条高亮，含优先级标记 |
| 🟡 | DeepSeek（执行）+ 先生（每日） | feishu 每日摘要 | 列表汇总，不逐条推送 |
| 🟢 白名单内 | DeepSeek 自执行 | 无需推送 | 在每日摘要末尾记录 |
| 🟢 白名单外 | 暂缓，先生下次对话确认 | 对话起始时提醒 | 简短列表 |

## 四、异常恢复

### 管道断裂处理

1. **发现断裂**：任何节点检测到前序节点超时无产出（Reflector >24h 未产出、flush >36h 未执行）
2. **自动诊断**：检查 cron 运行状态、脚本是否在位、配置文件完整性
3. **自动恢复**：管理员状态重建
4. **通知先生**：若自动恢复失败，标注 🔴 推送给先生

### 堆积治理项批量处理

- 治理项堆积超过 10 项时自动触发批量清理（先生确认后执行）
- 优先级顺序处理：先 🔴 → 🟡 → 🟢
- 同类操作批量执行（例如一次性更新所有头部日期）

## 五、健康检查

每日自动检查（由 Reflector 日常反思附带）：

| 检查项 | 正常 | 异常 |
|--------|:----:|:----:|
| Reflector 日产出 | <24h | >24h ⇒ 告警 |
| memory/ 日日志 | <36h | >36h ⇒ 告警 |
| tracker 无过期 pending | <48h | >48h ⇒ 提示 |
| 治理项堆积数 | <10 | ≥10 ⇒ 批量清理 |
| cron 任务状态 | error=0 | error≥1 ⇒ 告警 |

## 六、元管理层纪律（v1.1，08-02 追加）

### 变更六步流程

```
① 查 PROJECT_MAP（依赖影响）→ ② 查 VERSION_LEDGER（漂移现状）
→ ③ 执行变更 → ④ 更新 VERSION_LEDGER → ⑤ 写 DECISION_LOG（🔴/🟡级）
→ ⑥ 触发 L2 一致性检查
```

### 纪律细则

1. **回写时限**：任何落地动作（含补丁）完成后 24h 内回写 VERSION_LEDGER；违规记录进 findings/ → 周报点名 → 先生裁决
2. **L2 原则**：L2 是账本的消费者，不是生产者——只报告超时/疑似漂移，不下结论、不改账本状态（状态变更留给人）
3. **P0 豁免**：紧急修复先修后补（24h 内补记），元管理层不得成为效率杀手
4. **L2 升级机制**：🔴 待处理超 3 天周报标红；🔴 超 7 天自动进 findings；🟡 超 14 天自动进 findings；时限从"进入待处理状态"起算
5. **漂移率基线**：漂移率 = 未解决项/总数；考古期 ≤100%（预期）、清理后 ≤20%、验证期 ≤20%；连续 2 周超标 → 触发人工复盘
6. **考古分级**：🔴 级考古发现先给先生过目再入账；🟡 级直接入账本 + 周报汇总
7. **自指防护**：元管理层自身文件列入 VERSION_LEDGER 自检章节；每月元元检查由先生手动执行
8. **基准规则**：基准 = 各项目时间最新且已执行的方案。判定三层：① 时间最新 ② 文件名含 Final/最终 优先 ③ 仍有疑问 → 问先生。仅封版未执行的（第零章/3-A）标"待启动基准"，不参与配置对照
9. **流程必停点（LESSON-001 扩展）**：流程含"先生/GLM 提供/确认/评审"步骤时，必须先获得该角色输入才能继续；跳过=违规进 findings。不得以"先生可能不知道"或"自己能查到"为由跳过。考古/盘点类任务强制前置：输入核对清单（inventory/验证报告/governance/pending/handoff/reflections/long-term 全覆盖）→ 逐条对账 → 覆盖率≥90% 才可宣布完成
